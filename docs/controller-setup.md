# Simple controller setup

This checkout adds a native setup card to the existing controller applet on macOS and iOS. It builds on upstream `4b616bb`, independently of the earlier NX2Apple controller editor.

## Using the card

- The game request supplies the player range, permitted styles, supported player IDs, single-player flag and permission to use a pair. The player screen shows a tile per supported player within that range, with Ready / Not ready. The controller-type screen marks the current style as ◉ Selected, independently of readiness. Optional empty players do not prevent Apply once the minimum is ready; an occupied incompatible player does.
- Select a player, then Pro Controller, Joy-Con Pair, Joy-Con (L) or Joy-Con (R). Unsupported styles are dimmed and cannot be selected. A request with exactly one possible player skips the player grid.
- A pair asks whether to use one controller or two. One gamepad supplies the normal left and right controls and shares its motion across both sensors. With two devices, each keeps its own hand’s motion and rumble; when both devices are full gamepads, either device supplies left-stick input to the virtual left stick and right-stick input to the virtual right stick, as well as buttons for both halves. Releasing a button on one device does not cancel it while held on the other. This is a style/source selection UI, not a button-mapping editor.
- The device list marks Motion supported when GameController advertises a gyro. This is capability information, not proof the driver delivers samples. Identify appears for the focused device and is enabled when that device exposes haptics or a light; native Switch 2 devices briefly invert their player LED pattern. Raw HID devices without an identify mechanism remain listed, with Identify disabled.
- Devices with explicit assignments show their player number; automatic assignments have no player tag. A controller already explicitly used by another player can be moved; that player's old assignment is cleared. Borrowing an automatic player's device suppresses its automatic route instead of creating a second player with the same device.
- The D-pad and left stick navigate. GameController A selects, X identifies, **holding Y for 0.8 seconds applies** and **B goes back immediately; holding B for 0.8 seconds cancels at the root**. The footer order is Apply, Select, Cancel/Back; Apply and Cancel use the same ease-out fill. Controller-provided symbols show cross/circle/square/triangle on PlayStation devices. Mac also accepts arrows, Return/J, Escape/K held to go back/cancel, U for Identify and Space/I held to apply. Native buttons support touch and mouse; long-press Apply or Cancel; Back is immediate. Releasing early cancels a hold. Navigation, incompatibility or lost focus requires another release before starting a new hold.
- The launch screen also offers Configure Controllers under Controls (Advanced settings on macOS). Clicking it schedules setup and keeps the launch screen open: the button becomes Cancel, with a checkmark and “Configuration menu will open after game launch” beside it. Cancel removes the schedule and restores the original button. Pressing Play starts the host and opens the card before gameplay; Apply or Cancel then continues into the game. The schedule is held only in the current launcher view and is not saved as a preference. Startup cannot know controller restrictions the game has not published yet.
- Open the card manually from Controllers → Configure Controllers in the macOS menu bar, or Configure Controllers in the iOS gear menu’s Controls group. Manual editing uses the same Apply/Cancel flow with the currently supported styles. Its player range comes from the last game request, narrowed to the current reported players without going below the requested minimum; before the first request, it uses the current reported player count. An active controller request or editor takes priority; manual clicks never open a second card.

With Press a button to join, unjoined controllers remain listed and can be identified; their first button still joins using upstream's slot allocator. Controller merging remains an upstream setting: individual reassignment is unavailable while it merges all physical devices into one source.

A full gamepad used as a single Joy-Con adapts its controls to the side and the game’s current grip orientation, so it can stay upright. Real Joy-Cons retain native input.

## What stays upstream

With no manual selections, the route word is zero and all reads use the original resolver, including automatic player allocation, touch/keyboard merging, one-player fallback, Joy-Con splitting, motion calibration and existing transport ownership. A compatible game request still returns immediately. Player shortages use upstream’s joining popup first. After successful joining, incompatible controller types open SimpleUI. Type-only mismatches open SimpleUI directly. Canceling joining ends the request. Each stage has its own semaphore; the joining card is removed before SimpleUI opens. Only SimpleUI requires hold-to-apply.

Draft choices never change live input. Cancel leaves the committed routes unchanged. While setup holds input, vibration is suspended and pending motor values are cleared; closing it requires a fresh game vibration command and cannot override another suspension such as application inactivity. Physical hotplug continues to follow upstream allocation; disconnecting a manually used source suspends its assignment until it returns. Reconnection in the original slot restores the style when the controller model matches; a different model returns affected players to Automatic. Like upstream slot allocation, identical models cannot be distinguished across reconnection. Nothing is saved between app launches.

## Structure

`controller_setup.h` contains the small route encoding, readiness result and hold guard. One byte per player fits all eight routes in one atomic word. `hle_hid.c` resolves those routes when the game reads input, sensors, mouse or vibration handles. Physical source slots and their existing input, calibrated motion and haptic sinks stay intact. Apply validates before publishing the whole word; topology and capability changes are serialized against that publication.

`controller_setup_apple.h` contains the native AppKit/UIKit card and shared navigation flow. Both platforms retain upstream joining in `front_ctrl_support` and present style/source setup through `front_controller_setup` and retain the original game-thread wait, input ownership and release-before-return behavior. It uses Apple's public GameController glyphs and native controls; it does not embed private Apple Games app UI.

## Validation

Automated checks cover upstream HID behavior, manual source claims, one/two-device pairs, independent motion and rumble, invalid/duplicate routes, unplugging, input suppression and hold timing. The AppKit fixture covers the page flow, one-player skip, forbidden types, cancellation and draft invalidation. iOS source compilation and the unsigned synthetic production project build check compilation/linking only; there is no iOS simulator installed on this Mac.

The user tested controller setup on macOS and an iPhone 16 running iOS 27, including Jamboree and ARMS. A single gamepad supplies live samples to both virtual sensors, but ARMS motion control with that setup remains unresolved; two physical controllers work. These gameplay tests preceded the rebase onto `4b616bb`, which needs a fresh device retest. The fixture screenshots use simulated device names, not attached hardware. Game regression results and exact check outcomes are kept in the accompanying local validation report; a missing/old game shader package is not treated as a passing gameplay check.
